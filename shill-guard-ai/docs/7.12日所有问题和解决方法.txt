一、背景：什么是 thinking 模型
DeepSeek-R1、DeepSeek-v4-flash（带 thinking 的版本）、o1/o3 等模型，与普通 Chat 模型的本质区别是：

普通模型（GPT-4o、DeepSeek-V2.5 等）：

输入 prompt → 直接输出 answer
Thinking 模型（DeepSeek-R1、v4-flash thinking 版）：

输入 prompt → 先输出 <think>...推理过程...</think> → 再输出 answer
模型在内部会先生成一段"思考链"（CoT），然后再给出最终回答。这是它更强的原因，也是导致后续问题的根本原因。

二、第一种结构化输出失败：function_calling
它是什么
with_structured_output(method="function_calling") 在底层会把你的 Pydantic schema 转换成一个 OpenAI function definition，然后给 API 发送：

{
  "tools": [{"type": "function", "function": {"name": "WorkerContextResult", "parameters": {...}}}],
  "tool_choice": {"type": "function", "function": {"name": "WorkerContextResult"}}
}
tool_choice: required 的含义是：强制模型必须调用这个函数，不允许它输出普通文本。

为什么 thinking 模型不支持
Thinking 模型的架构决定了它的输出分两个阶段：

第一阶段：生成 <think> 推理链（纯文本流）
第二阶段：生成最终 answer
OpenAI 协议里，tool_calls 是 assistant message 的一种特殊类型，与文本输出互斥。但 thinking 模型必须先输出一段思考文本，然后才能调用 function。这两个约束在协议层面冲突了——模型既要先输出文本（思考链），又要被 tool_choice: required 强制"只能调 function 不能输出文本"。

DeepSeek 官方在 API 文档里明确写了：

thinking 模式下不支持 tool_choice 参数

API 直接返回 400：

Thinking mode does not support this tool_choice
三、第二种结构化输出失败：json_mode
它是什么
with_structured_output(method="json_mode") 换了一种方式，给 API 发送：

{
  "response_format": {"type": "json_object"}
}
它不再强制 function call，而是告诉模型"你的输出必须是合法 JSON 字符串"。

为什么 thinking 模型也不支持
根本原因相同：thinking 模型的第一阶段输出（<think> 推理链）是自由格式的纯文本，不是合法 JSON。

response_format: json_object 的语义是"整个 assistant response 必须是 JSON"，但 thinking 模型的完整响应是：

<think>让我想想，用户问的是名字，背景里有"张三"，所以...</think>
{"has_relevant_context": true, "background_fact": "用户名字是张三"}
前面的 <think>...</think> 破坏了"整个输出是 JSON"的约束。所以 API 拒绝了这个请求，同样返回 400。

（注：部分 API 实现里，<think> 内容会被剥离后单独放在 reasoning_content 字段，不混入 content。但 json_mode 的校验发生在 API 层，思考链的生成本身就与 json_object 格式不兼容，所以直接拒绝。）

四、为什么之前没发现，今天才暴露

deepseek-v4-flash 这个模型名对应的是 DeepSeek 最新发布的 Flash 版本，默认开启 thinking 模式。在你 .env 里配置的 API 端点（百炼 / DeepSeek 官方）将这个模型名路由到了 thinking 版本。

    "...规则...\n"
    "必须只返回如下格式的 JSON，不要任何额外说明：\n"

resp = await llm.ainvoke([SystemMessage(...), HumanMessage(...)])
content = resp.content   # 可能包含 <think>...</think> + JSON
# 正则从文本中抠出 JSON 块，忽略思考链前缀
match = _JSON_RE.search(content)
data = json.loads(match.group())
result_obj = WorkerContextResult(**data)
thinking 模型输出的完整内容是：

正则 \{[^{}]*"has_relevant_context"[^{}]*\} 跳过思考链，精确匹配到后面的 JSON 块，解析成功。

这就是为什么这个方案对所有模型都兼容——它完全不依赖 API 协议层的结构化输出特性，只依赖模型理解 prompt 的能力。

用一个具体的比喻来解释。

先理解"普通模型"是怎么调 function 的
普通模型（非 thinking）收到请求后，它的输出只有两种选择：

选择 A：输出普通文本

assistant: {
  "content": "你好，我是 AI 助手，有什么可以帮你的？",
  "tool_calls": null
}
选择 B：调用函数（tool_calls）

assistant: {
  "content": null,
  "tool_calls": [{
    "name": "WorkerContextResult",
    "arguments": "{\"has_relevant_context\": true, \"background_fact\": \"用户名字是张三\"}"
  }]
}
注意：content 和 tool_calls 二选一，这是 OpenAI 协议的硬性规定。当你传 tool_choice: required 时，就是强制走选择 B，content 必须为 null。

普通模型完全没问题——它想好答案后，直接输出 JSON 参数就行了。

再理解"thinking 模型"的输出结构
Thinking 模型（DeepSeek-R1、o1 等）有个特殊之处：它必须先"想"，再"答"。

它的完整输出在协议上是这样的：

assistant: {
  "reasoning_content": "让我想想...用户问的是名字，背景里有张三，所以答案是...",
  "content": "用户名字是张三。",
  "tool_calls": null
}
reasoning_content（思考链）是一个独立的文本字段，而且它必须在 content 之前生成，因为思考链就是为了推导出最终答案的。

冲突在哪里
现在问题来了。当你要求 tool_choice: required 时，协议要求：

content = null        ← 必须为空
tool_calls = [...]    ← 必须有内容
但 thinking 模型的输出是：

reasoning_content = "..." ← 这是文本，必须有
content = null            ← 可以为空，没问题
tool_calls = [...]        ← 也可以有，理论上没问题
表面上看没有冲突？

问题出在 reasoning_content 上。

DeepSeek 的 API 实现里，思考链（reasoning_content）和最终答案（content 或 tool_calls）是同一个 generation pass 里生成的。模型在生成时无法切换"输出模式"。

也就是说，thinking 模型的生成顺序是这样的：

token 1~N:   "让我想想...用户问名字..."   → 这是 reasoning_content（文本流）
token N+1~M: "用户名字是张三"             → 这是最终答案
而 tool_calls 要求的输出格式是结构化的 JSON 参数，不是自然语言文本：

token N+1~M: {"has_relevant_context": true, "background_fact": "用户名字是张三"}
DeepSeek 的 thinking 模型在训练时，思考链之后只学习了输出自然语言答案，没有学习"思考完再输出 function call JSON"这个模式。所以当你强制要求它走 tool_calls 路径时，模型本身就不会做，API 直接拦截返回 400。

用一个现实比喻
想象你雇了两种员工来填一张表格：

普通员工（普通模型）：

你说"填这张表"，他直接拿起笔填好交给你。没有废话，直接给结构化输出。

思考型员工（thinking 模型）：

你说"填这张表"，他先在草稿纸上打了一大段草稿（reasoning_content），把逻辑理顺之后，最后才在表格上填写答案（content）。

现在你要求"只能填表格，不许先写草稿"（tool_choice: required = 强制 tool_calls，content 必须 null）：

对普通员工：没问题，他本来就直接填表。
对思考型员工：他做不到。他的工作方式就是先打草稿再填表，你不让他打草稿，他就不知道怎么填了。
DeepSeek 的 API 也知道这一点，所以直接告诉你：

400: Thinking mode does not support this tool_choice
翻译过来就是："这个员工只会先想后答，你不能强制他跳过想的步骤直接输出结构化表单。"

为什么新方案可行
新方案不再"强制"任何东西，而是换了一种说话方式：

system: "你必须只返回这种格式的 JSON：{'has_relevant_context': ..., 'background_fact': '...'}"
human:  "用户问了名字，背景里有张三，请提炼"
这时 thinking 员工的工作流程变成：

草稿（reasoning_content）：
  "让我分析一下...用户问名字...背景有张三...所以应该返回 JSON，
   has_relevant_context 为 true，background_fact 填'用户名字是张三'..."
最终答案（content）：
  {"has_relevant_context": true, "background_fact": "用户名字是张三"}
他仍然先思考，然后输出 JSON 文本——不是通过 tool_calls 机制，而是把 JSON 当普通文本输出。我们再用正则从 content 里把 JSON 抠出来解析。

核心区别：

方式	强制协议层	要求模型做什么	结果
tool_choice: required
是
跳过文本直接输出 function call
模型做不到，400
response_format: json_object
是
整个输出必须是 JSON
思考链破坏格式，400
新方案（prompt 约束）
否
自己决定先思考再输出 JSON 文本
完全没问题
本质上：协议层的强制约束 vs. prompt 层的软性引导。thinking 模型不接受协议层约束，但完全理解并遵守 prompt 指令。

根因分析
之前的修复为什么不够
之前只做了"从第一个 HumanMessage 开始"：

first_human = next(...)
window = window[first_human:]   # 只截掉了开头
这只解决了开头的孤儿，没有解决内部的孤儿。

这次错误的具体场景
window=6/19 msgs → 19条消息，触发了摘要压缩（19-1=18 > 8）。

to_summarize = history[:12]，切割点落在第 12 条。如果第 12 条恰好是 AIMessage(tool_calls)（联网搜索），而第 13 条是对应的 ToolMessage：

to_summarize = [..., AIMessage(tool_calls)]   ← 被 RemoveMessage 删掉
keep         = [ToolMessage, AIMessage, ...]  ← ToolMessage 变成孤儿，留在 state 里
state["messages"] 变成：

[ToolMessage(孤儿), AIMessage, HumanMessage, AIMessage, HumanMessage(current), ...]
窗口取 [-6:] = [ToolMessage, AIMessage, HumanMessage, AIMessage, HumanMessage, HumanMessage(current)]

first_human 找到 index=2，截后 = [HumanMessage, AIMessage, HumanMessage, HumanMessage(current)] → 没问题，孤儿被跳过了。

但是，另一种场景：

to_summarize 末尾 = AIMessage(tool_calls)  ← 删掉
keep 开头          = ToolMessage            ← 孤儿
keep 中间          = HumanMessage
keep 后面          = AIMessage(tc), ToolMessage   ← 这是正常的工具调用对
窗口 = [ToolMessage(孤儿), HumanMessage, AIMessage(tc), ToolMessage, HumanMessage(current)]

first_human 找到 index=1 → 截后 = [HumanMessage, AIMessage(tc), ToolMessage, HumanMessage(current)] → 这是合法的！不应该出错才对。

实际上问题在 to_summarize 切割点：旧代码用纯下标 history[:-6] 切割，没有保证切割点是 HumanMessage 边界。这次修复同时修了两处：

memory_node

chat_node (_sanitize_window)
