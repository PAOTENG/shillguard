## 问题一：Worker LLM 结构化输出报 400（thinking 模型兼容性）

### 现象

服务运行时，终端出现：

```
[ContextProcessor] 结构化提炼失败，降级为空:
Error code: 400 - {'error': {'message': 'Thinking mode does not support this tool_choice', ...}}
```

Agent 开始"失忆"——无论用户之前说了什么名字、背景，AI 都回答"我不知道"。

### 背景

`context_processor_node`（Worker LLM 节点）负责从 mem0 记忆、历史摘要、RAG 片段中提炼出一句关键背景，写入 `processed_context`，供 Main LLM 使用。

为了强制 Worker LLM 只输出结构化 JSON（`WorkerContextResult`），最初使用了 LangChain 的 `with_structured_output`。

### 根因：两种结构化输出方式全部与 thinking 模型不兼容

**第一种：`method="function_calling"`**

底层发送给 API 的请求：
```json
{
  "tools": [{"type": "function", "function": {"name": "WorkerContextResult", ...}}],
  "tool_choice": {"type": "function", "function": {"name": "WorkerContextResult"}}
}
```
`tool_choice: required` 要求模型输出必须是 `tool_calls`，不能输出普通文本。

但 thinking 模型（deepseek-v4-flash）的输出分两阶段：
1. 先生成 `<think>...推理链...</think>`（纯文本流）
2. 再生成最终答案

这两个阶段与"`必须只输出 tool_calls，不能输出文本`"的协议约束直接冲突。DeepSeek 官方文档明确说明 thinking 模式不支持 `tool_choice`，API 直接返回 400。

**第二种：`method="json_mode"`（修复后再次失败）**

底层发送：
```json
{"response_format": {"type": "json_object"}}
```
语义是"整个 assistant response 必须是合法 JSON"。但 thinking 模型的完整响应是：
```
<think>让我想想...背景里有张三...</think>
{"has_relevant_context": true, "background_fact": "用户名字是张三"}
```
前面的 `<think>...</think>` 破坏了"整个输出是 JSON"的约束，API 同样返回 400。

**附加问题：`@lru_cache` 使修复不生效**

改完 `json_mode` 后，`_get_structured_worker_llm` 函数使用了 `@lru_cache` 缓存，进程内已经缓存了旧的 `function_calling` 版本 LLM 实例，改动不会生效，必须重启服务才能看到效果。这给调试造成了很大的干扰。

### 尝试过的方案

| 方案 | 结果 |
|---|---|
| `with_structured_output(method="function_calling")` | 400：不支持 tool_choice |
| 改为 `with_structured_output(method="json_mode")` | 400：思考链破坏 JSON 格式 |
| 重启服务清除 lru_cache 后再试 json_mode | 仍然 400 |

### 最终解决方案

**完全放弃 `with_structured_output`**，改为"prompt 内嵌 JSON schema + 手动正则提取"：

**`_WORKER_SYSTEM` 直接在 system prompt 里给出 JSON 格式示例：**
```python
_WORKER_SYSTEM = (
    "你是信息提炼助手。...\n"
    "必须只返回如下格式的 JSON，不要任何额外说明：\n"
    '{"has_relevant_context": true, "background_fact": "单句事实"}\n'
    '或 {"has_relevant_context": false, "background_fact": ""}'
)
```

**正则从模型的原始文本响应中提取 JSON：**
```python
_JSON_RE = re.compile(r'\{[^{}]*"has_relevant_context"[^{}]*\}', re.DOTALL)

resp = await llm.ainvoke([SystemMessage(...), HumanMessage(...)])
content = resp.content  # 可能包含 <think>...</think> + JSON
match = _JSON_RE.search(content)
data = json.loads(match.group())
```

正则会跳过 `<think>...</think>` 前缀，精确匹配后面的 JSON 块。这个方案对所有模型（thinking / 非 thinking）全部兼容，因为它完全不依赖 API 协议层的结构化约束。

同时移除了 `@lru_cache`，避免缓存旧实例。

## 问题二：mem0 search API 变更导致记忆检索失败

### 现象

终端出现警告：
```
[mem0] 检索记忆失败（已跳过）:
Top-level entity parameters frozenset({'user_id'}) are not supported in search().
Use filters={'user_id': '...'} instead.
```

Agent 检索不到任何长期记忆，`long_term_memories` 始终为空。

### 根因

`mem0` 库升级后，`search()` 方法不再接受 `user_id` 作为顶层关键字参数。旧代码：

```python
results = mem0.search(query, user_id=user_id, limit=settings.mem0_search_limit)
```

新版本 API 要求用 `filters` 字典：

```python
results = mem0.search(query, filters={"user_id": user_id}, limit=settings.mem0_search_limit)
```

### 解决方案

修改 `app/agents/chat/memory.py` 中的 `search_memories` 函数，将 `user_id=user_id` 改为 `filters={"user_id": user_id}`。

## 问题三：mem0 数据存储字段变更导致内容提取失败

### 现象

即使解决了 API 变更问题，`search_memories` 的返回值也始终为空字符串，`processed_context` 为空。通过诊断脚本检查 mem0 返回的原始数据，发现：

```python
m.get("memory")  # None
m.get("text")    # None
m.get("documents")  # None
```

但 `m.get("data")` 有内容。

### 根因

mem0 新版本将记忆文本存储在 `metadata['data']` 字段（或直接在结果字典的 `data` 键），而旧的提取逻辑只尝试 `memory`、`text`、`documents` 三个字段，导致提取到的内容始终为 `None`，最终拼接成空字符串。

### 解决方案

更新 `search_memories` 中的数据提取逻辑，增加对 `data` 字段的支持：

```python
content = (
    m.get("memory")
    or m.get("text")
    or m.get("data")   # ← 新增，兼容新版本 mem0
    or ""
)
```

## 问题四：Agent 忘记用户名字（processed_context 始终为空的综合症）

### 现象

用户说"我叫张三"，之后问"我叫什么名字"，AI 回答"你没有告诉过我你的名字"。

### 根因（多因叠加）

这是上述三个问题（问题一、二、三）的综合结果：

1. **Worker LLM 400 错误** → `processed_context` 降级为空
2. **mem0 API 变更** → `long_term_memories` 检索失败为空
3. **mem0 数据字段变更** → 即使检索成功，也提取不到文本

三个问题同时存在，导致 `context_processor_node` 无论如何都得不到有效背景，最终 Main LLM 在没有任何记忆的情况下回答问题。

### 解决方案

依次修复上述三个问题后，记忆功能全面恢复。

## 问题五：代码输出为纯文本而非代码块格式

### 现象

让 AI 写代码，输出是：

```
def bubble_sort(arr):
    n = len(arr)
    ...
```

而不是高亮格式的代码块，没有语法高亮，可读性差。

### 根因

1. **System Prompt 未明确要求 Markdown 代码块**：LLM 没有收到指令要用代码块包裹代码。
2. **前端未渲染 Markdown**：即使 LLM 输出了 Markdown 格式，前端 `white-space: pre-wrap` 样式也只会原样显示 `` ``` `` 符号，不会渲染为 HTML `<pre><code>` 标签。

### 解决方案

**后端（`prompts.py`）：** 在 `SYSTEM_PROMPT` 中增加规则：

```python
"9. 输出代码时必须使用 Markdown 代码块格式（```语言名）。"
```

**前端（`index.html`）：**
1. 引入 `marked.js`（Markdown → HTML）和 `highlight.js`（语法高亮）CDN
2. 配置 `marked.setOptions({ gfm: true, highlight: hljs.highlightAuto })`
3. 在 `readSSE` 函数中，当 `renderMarkdown=true` 时，用 `marked.parse()` 渲染累积文本，设置 `outEl.innerHTML`，并对新 `<code>` 块调用 `hljs.highlightElement`
4. 移除 `.output` 的 `white-space: pre-wrap`，改为支持 HTML 元素的 Markdown 样式

## 问题六：BadRequestError "tool must follow tool_calls"——三次递进的同根问题

这个错误一共出现了**三次**，每次都是同一个根因的不同侧面，每次修复都只堵住了当时已知的漏洞，下一次暴露出更深的边界情况。以下完整记录三次出现的前因后果和最终的彻底修复。

---

### 背景知识：OpenAI 协议对工具消息的约束

LangGraph 中每次联网搜索（Tavily）会在消息列表里留下一对：

```
AIMessage(tool_calls=[{id: "call_A"}, ...])   ← 发起工具调用
ToolMessage(tool_call_id="call_A", ...)        ← 工具返回结果
```

OpenAI API 有两条硬性规定：
1. `role=tool` 的消息**必须**紧跟在包含 `tool_calls` 的 `role=assistant` 消息之后
2. 一个 `AIMessage` 里有几个 `tool_calls`，后面就必须有对应数量且 ID 全部匹配的 `ToolMessage`

违反任意一条，都会返回 400。

---

### 第一次出现

**错误信息：**
```
"Messages with role 'tool' must be a response to a preceding message with 'tool_calls'"
```

**根因：滑动窗口开头出现孤立 ToolMessage**

`chat_node` 从全部消息中取最后 6 条发给 LLM。如果这 6 条的第一条恰好是一个 `ToolMessage`（其前驱 `AIMessage(tool_calls)` 不在窗口里，或已被 `RemoveMessage` 删掉），就触发了规则 1。

```
完整 state:  [..., AIMessage(tc), ToolMessage, HumanMessage, AIMessage, HumanMessage(当前)]
取最后 6 条:        [AIMessage(tc), ToolMessage, HumanMessage, AIMessage, HumanMessage(当前)]
                   ↑ 没问题，配对完整

另一种情况:
完整 state:  [...被删..., ToolMessage(孤儿), HumanMessage, AIMessage, HumanMessage(当前)]
取最后 6 条:  [ToolMessage(孤儿), ...]  ← 开头就是孤立 ToolMessage → 400
```

**当时的修复（不完整）：**

```python
first_human = next((i for i, m in enumerate(window_messages) if isinstance(m, HumanMessage)), 0)
window_messages = window_messages[first_human:]  # 从第一个 HumanMessage 开始截
```

只解决了**窗口开头**的孤立情况，没有处理窗口内部。

---

### 第二次出现

**错误信息：**（同上，同一个 400 报错）
```
"Messages with role 'tool' must be a response to a preceding message with 'tool_calls'"
```
终端日志中同时出现：`window=6/19 msgs`，说明触发了摘要压缩（19-1=18 > 8）。

**根因：两个新场景都未被覆盖**

**场景 A：摘要切割点拦腰截断工具调用对**

旧代码用简单下标切割：`to_summarize = history[:-6]`，不保证切割点落在 `HumanMessage` 边界。如果切割点恰好夹在工具调用对中间：

```
history:  [..., AIMessage(tool_calls), ToolMessage, HumanMessage, ...]
                ↑ 切割点落这里
                  AIMessage 进 to_summarize → 被 RemoveMessage 删掉
                                  ↑ ToolMessage 留在 state 里 → 孤儿
```

**场景 B：窗口内部孤立 ToolMessage**

`first_human` 截断只处理开头，但孤立 ToolMessage 也可能出现在窗口中间（如 keep 区的第一条是 `HumanMessage`，但其后某处有孤立 `ToolMessage`），此时截断后内部仍有问题。

**这次的修复：**

**修复点一：`memory_node` 切割点左移对齐 HumanMessage**

```python
cut = len(history) - settings.keep_recent_messages
while cut > 0 and not isinstance(history[cut], HumanMessage):
    cut -= 1  # 向左移直到 keep 区以 HumanMessage 开头
to_summarize = history[:cut]
```

**修复点二：引入 `_sanitize_window` 全量扫描**

用顺序扫描逻辑清理窗口：
- 从第一个 HumanMessage 开始
- 逐条扫描，遇到 ToolMessage 时检查 `cleaned[-1]` 是否是 AIMessage(tool_calls)，否则丢弃
- 移除末尾悬空的 AIMessage(tool_calls)

**仍然不够完整的原因：** 顺序扫描中，当 AIMessage 有**多个** tool_calls 时，第 2 个 ToolMessage 的前驱 `cleaned[-1]` 是第 1 个 ToolMessage，不是 AIMessage，会被错误丢弃。这个边界情况在第三次出现时才被触发。

---

### 第三次出现

**错误信息（新变体！）：**
```
"An assistant message with 'tool_calls' must be followed by tool messages responding
to each 'tool_call_id'. (insufficient tool messages following tool_calls message)"
```

注意：这次错误和前两次**措辞不同**——前两次是"ToolMessage 没有前驱"，这次是"AIMessage 的 tool_calls 没有足够多的 ToolMessage 响应"。这是规则 2 的违反。

**根因：顺序扫描逻辑的致命缺陷**

当 LLM 同时发起两个工具调用（如两次并行搜索）时：

```
state:  AIMessage(tool_calls=[call_A, call_B])
        ToolMessage(tool_call_id=call_A)
        ToolMessage(tool_call_id=call_B)
```

旧 `_sanitize_window` Step 2 的顺序扫描逻辑：

```python
for msg in msgs:
    if isinstance(msg, ToolMessage):
        if cleaned and getattr(cleaned[-1], "tool_calls", None):
            cleaned.append(msg)  # 只检查"前一条是否是 AIMessage(tool_calls)"
```

处理 `ToolMessage(call_A)` 时：`cleaned[-1]` = AIMessage → 保留 ✓
处理 `ToolMessage(call_B)` 时：`cleaned[-1]` = ToolMessage(call_A) → **被错误丢弃！**

结果：`cleaned` 里变成 `[AIMessage(two calls), ToolMessage(call_A)]`，call_B 没有对应响应，触发 400。

**根本问题：顺序扫描把"一个 AIMessage + 多个 ToolMessage"的原子单元拆散了。**

---

### 最终彻底修复：原子化处理工具调用组

把 `_sanitize_window` 重写为"前向看 + 原子组"模式：

```python
def _sanitize_window(messages):
    # Step 1：从第一个 HumanMessage 开始
    start = next((i for i, m in enumerate(messages) if isinstance(m, HumanMessage)), 0)
    msgs = list(messages[start:])

    # Step 2：原子化处理工具调用组
    cleaned = []
    i = 0
    while i < len(msgs):
        msg = msgs[i]

        if isinstance(msg, ToolMessage):
            # 孤立 ToolMessage（未被 AIMessage 分支预先收集）→ 直接丢弃
            i += 1

        elif isinstance(msg, AIMessage) and getattr(msg, "tool_calls", None):
            # 收集该 AIMessage 期望的所有 tool_call_id
            expected_ids = {tc["id"] for tc in msg.tool_calls}

            # 向前看：收集紧跟其后的所有连续 ToolMessages
            j = i + 1
            following = []
            while j < len(msgs) and isinstance(msgs[j], ToolMessage):
                following.append(msgs[j])
                j += 1

            satisfied_ids = {tm.tool_call_id for tm in following if hasattr(tm, "tool_call_id")}

            if expected_ids == satisfied_ids:
                # 完整工具调用组 → 整组保留
                cleaned.append(msg)
                cleaned.extend(following)
            # else：不完整 → 整组丢弃（AIMessage + 所有 ToolMessages 全不加入）

            i = j  # 跳过已处理的 ToolMessages

        else:
            cleaned.append(msg)
            i += 1

    # Step 3：移除末尾仍然悬空的 AIMessage(tool_calls)
    while cleaned and getattr(cleaned[-1], "tool_calls", None):
        cleaned.pop()

    return cleaned
```

**关键变化：**

| 旧版（顺序扫描） | 新版（原子组） |
|---|---|
| 逐条检查"前一条是否是 AIMessage" | 遇到 AIMessage(tool_calls) 时先向前看，收集所有对应 ToolMessages |
| 第 2+ 个 ToolMessage 会被误判为孤立而丢弃 | 所有 tool_call_id 都满足才整组保留，否则整组丢弃 |
| 无法处理多 tool_calls 场景 | 完整处理任意数量的并行工具调用 |

---

### 三次出现的对比总结

| 次数 | 错误消息关键字 | 触发场景 | 根本原因 | 修复方案 |
|---|---|---|---|---|
| 第1次 | `tool must be a response to tool_calls` | 滑动窗口开头是孤立 ToolMessage | 窗口起点不固定 | 从第一个 HumanMessage 处截断 |
| 第2次 | `tool must be a response to tool_calls` | 摘要切割点拦腰截断 tool 对；内部孤立 ToolMessage | 切割点不对齐 HumanMessage；顺序扫描只处理开头 | 切割点左移对齐 + `_sanitize_window` 全量扫描 |
| 第3次 | `insufficient tool messages following tool_calls` | AIMessage 有多个 tool_calls，第 2+ 个 ToolMessage 被顺序扫描错误丢弃 | 顺序扫描把原子工具调用组拆散了 | 重写为原子组处理：前向看 + 完整性校验 |

## 问题八：chatAgent 响应速度很慢（TTFT 达 7000ms+）

### 现象

用户反映 AI 回复非常慢，从发消息到看到第一个字（TTFT）需要 7 秒以上。

### 性能测试

编写了 `scripts/perf_test.py`，独立测量各组件耗时，结果如下：

| 组件 | 耗时 | 状态 |
|---|---|---|
| PostgreSQL 建连/查询 | 27ms / 6ms | OK |
| Embedding API（百炼） | 264ms | OK |
| RAG 全链路（embed+BM25+rerank） | 1022ms | WARN |
| **mem0 search** | **2793ms** | **SLOW（最大瓶颈）** |
| Worker LLM（JSON 提炼） | 1433ms | OK |
| Main LLM TTFT | 1621ms | OK |

### 根因分析

**TTFT 瓶颈叠加公式：**
```
TTFT ≈ memory_node + rag_node + context_processor + Main_LLM_TTFT
     ≈   2793ms    +   611ms  +     1433ms        +    1621ms
     ≈   6458ms
```

四个节点全部**串行执行**，而且前三个节点全都在 Main LLM 开始输出之前完成，用户要等足足 5-6 秒才能看到第一个字。

**具体分析：**

1. **mem0 search = 2793ms（最严重）**：mem0 内部不仅有向量检索，还会调用 LLM 进行记忆实体提取，LLM 调用是主要耗时来源。而 `memory_node` 和 `rag_node` 是**完全独立**的，却排在串行流水线上。

2. **RAG = 1022ms**：embed（264ms）+ BM25 网络 RTT 到远程 ES（300-700ms）+ rerank（270ms）。

3. **Worker LLM = 1433ms**：每次对话都多调一次 LLM。即使背景为空，旧代码里 `user_said` 必然存在（用户有发言记录），`if not any([memories, summary, rag, user_said])` 这个条件永远为 False，Worker LLM 永远不会被跳过。

### 解决方案

**优化一：`memory_node` 与 `rag_node` 并行化（最关键）**

两者写入不同 state 字段（`long_term_memories/summary` 和 `rag_context`），完全独立，可以并行。

旧图（串行）：
```
START → memory → rag → context_processor → chat
```

新图（fan-out 并行）：
```
        ┌── memory ──┐
START ──┤            ├── context_processor → chat
        └──  rag   ──┘
```

LangGraph 实现只需修改 `build_graph` 中的边：

```python
# 旧代码
g.set_entry_point("memory")
g.add_edge("memory", "rag")
g.add_edge("rag", "context_processor")

# 新代码：fan-out 并行
g.add_edge(START, "memory")
g.add_edge(START, "rag")
g.add_edge("memory", "context_processor")
g.add_edge("rag", "context_processor")
# context_processor 自动等待两者全部完成（LangGraph fan-in 语义）
```

**优化二：无外部背景时跳过 Worker LLM**

Worker LLM 的价值在于提炼 Main LLM"看不到的"外部背景（mem0 记忆、历史摘要、RAG 片段）。`user_said` 是当前窗口的发言记录，Main LLM 本身就能看到消息历史，不需要 Worker 提炼。

```python
# 旧条件：user_said 必然存在，永远不跳过
if not any([memories, summary, rag, user_said]):
    return {"processed_context": ""}

# 新条件：只看外部背景，user_said 不算
if not any([memories, summary, rag]):
    print("[ContextProcessor] 跳过 Worker LLM（仅 user_said，无外部背景）")
    return {"processed_context": ""}
```

**效果验证（优化前后对比）：**

| 轮次 | 优化前 TTFT | 优化后 TTFT | 改善 |
|---|---|---|---|

## 今日核心教训

1. **thinking 模型有协议约束**：任何需要 LLM 输出结构化数据的地方，都应该默认使用"prompt 内嵌 schema + 手动解析"方案，而不是依赖 `with_structured_output`，因为后者依赖 API 层协议，而 thinking 模型与这些协议存在根本冲突。

2. **lru_cache 是隐形陷阱**：在需要热更新的 LLM 实例上使用 `@lru_cache` 会导致修改不生效，调试时很难发现。应明确区分"配置不变的全局单例"和"可能动态变化的实例"。

3. **同一根因会以不同变体反复出现**：tool 消息结构错误出现了三次，每次报错措辞微妙不同（ToolMessage 孤立 vs. tool_calls 响应不足），说明修复时要从**根本机制**出发（工具调用是原子单元），而不是针对每个具体症状打补丁。最终的原子组方案才是真正的根治。

4. **顺序扫描不能处理原子性约束**：旧的逐条扫描逻辑（"前一条是不是 AIMessage"）无法感知多 tool_calls 场景，必须改为前向看（look-ahead）的分组处理，把 AIMessage + 所有对应 ToolMessages 视为不可分割的原子单元。

5. **串行流水线是 TTFT 最大杀手**：即使每个节点单独很快，串行叠加后 TTFT 也会非常高。要养成识别"独立节点"的习惯，尽可能并行化。

6. **第三方库 API 变更是常态**：mem0、langchain 等库都会悄悄改接口，出现莫名其妙的"记忆失效"时，优先检查 API 是否有变更，而不是只看业务逻辑。
