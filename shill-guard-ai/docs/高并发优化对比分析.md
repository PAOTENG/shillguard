## 三、核心结论

### ✅ P0 异步改造的真实收益
1. **LLM 调用不再阻塞事件循环**：10 并发下 health p50 从 14ms → 6ms，p95 从 120ms → 7ms，证明 `ainvoke` 让事件循环在 LLM HTTP 等待期间能继续响应其它请求。这是 P0 的核心目标，**达成**。
2. **单并发功能正确**：1 用户 4/4 成功，TTFT 8.3s，与单测基线一致，异步改造没有破坏功能。

### ❌ 没有达成的预期
1. **chat 并发能力没有提升，反而略降**：
   - 10 并发失败率 55% → 78%
   - 10/100/500 并发 TTFT p50 都比优化前更慢（30→41s、42→57s、42→60s）
   - 50/300/1000 并发下优化后甚至 0 个请求在 60s 内完成
2. **高并发下 health 反而略差**（300/500 并发 p50 上升 16~22%）

### 根因：真正的瓶颈是 reranker，不是事件循环阻塞
P0 解决了"LLM 同步调用阻塞事件循环"，但暴露出**第二个、更硬的瓶颈——reranker（FlagReranker / torch）**：

- rerank 是 **CPU 密集型**，torch 推理持有 **GIL**（全局解释器锁）
- `asyncio.to_thread(rerank)` 只是把 rerank 丢到线程池，**线程间仍受 GIL 串行化**
- 多个并发 rerank 抢 GIL，还会**抢占事件循环线程的 GIL 时间** → 高并发下事件循环也被拖累（health p95 在 300 并发飙到 870ms）
- 单进程 + GIL = rerank 实际是串行的，并发越多排队越久

**一句话**：P0 是"必要但不充分"。它解除了 LLM 阻塞，但 reranker 的 GIL 绑定成为新瓶颈，async 对 CPU/GIL 绑定的代码无能为力。

## 四、最终方案：rerank 改远程 API（全链路异步化）

### 4.0 方案选择
受限于硬件（16GB RAM 仅剩 1.5GB、GTX 1650 Ti 4GB 显存），多 worker 不可行。
改用远程 rerank API（硅基流动 SiliconFlow，同款 `BAAI/bge-reranker-v2-m3` 模型），
把 rerank 从"本地 torch CPU 活"变成"异步 HTTP I/O"，彻底消除 GIL 瓶颈。

### 4.1 改造内容
| 文件 | 改动 |
|---|---|
| `app/config.py` | 新增 `siliconflow_api_key` / `siliconflow_rerank_url` |
| `app/rag/reranker.py` | 新增 `rerank_api()` 异步函数（httpx 调 API，失败降级本地） |
| `app/rag/retriever.py` | `asyncio.to_thread(rerank)` → `await rerank_api()` |

### 4.2 最终压测结果（全档三版对比）

| 并发 | 优化前(本地rerank) | 优化后(本地rerank) | **API rerank** |
|---|---|---|---|
| 10 | 55% 失败, TTFT 30s | 78% 失败, TTFT 41s | **0% 失败, TTFT 2.8s** ✅ |
| 50 | 84% 失败, TTFT 47s | 卡死(0完成) | **0% 失败, TTFT 8.5s** ✅ |
| 100 | 100% 失败, 42s | 100% 失败, 57s | 97% 失败, 40s |
| 300 | 100% 失败, 31s | 卡死 | 100% 失败, 46s |
| 500 | 100% 失败, 42s | 100% 失败, 60s | 100% 失败, 41s |
| 1000 | 100% 失败, 48s | 卡死 | 100% 失败, 49s |

### 4.3 结论分两段

**第一段（10~50 并发）：优化大成功**
- 10 并发：失败率 55%→0%，TTFT 30s→2.8s（10.7×）
- 50 并发：失败率 84%→0%，TTFT 47s→8.5s（5.5×）
- GIL 瓶颈彻底解决，全链路异步化达成

**第二段（100+ 并发）：遇到外部 API 容量瓶颈（非应用层问题）**
- 事件循环健康度（health p50）始终在 11~370ms，证明 GIL 已无阻塞
- 100+ 失败原因是外部 LLM API 的并发容量限制（TTFT 在 provider 侧排队）
- 突破 100 并发需：升级 DeepSeek API 等级 / 多 key 负载均衡 / 请求背压队列

## 五、二次诊断：100+ 并发的真凶是 DeepSeek LLM 退化

### 5.1 分步计时实验
在 `retrieve`（embed+bm25、rerank）和 `chat_node`（llm_ainvoke）三步加 `[TIMER]` 计时，
对比单并发 vs 100 并发各步骤耗时：

| 步骤 | 单并发基线 | 100并发时 | 变化 | 判定 |
|---|---|---|---|---|
| embed+bm25 | 250ms | 190~1500ms | ~3-4x | ✅ 正常网络抖动 |
| rerank | 280ms | 565~1437ms | ~3-4x | ✅ 正常网络抖动 |
| **llm_ainvoke** | **2500ms** | **5039~46725ms** | **2~18x** | ❌ **暴涨** |

llm_ainvoke 随并发递增轨迹：5039 → 8169 → 16453 → 24703 → 32867 → 42572 → **46725ms**。

### 5.2 根因
DeepSeek v4-flash 的 2500 并发是**硬上限**（超过才报 429），100 并发远没碰到。
但 LLM 推理是 GPU 密集型，100 个请求同时来，DeepSeek 的 GPU 分时复用服务，
单请求耗时从 2.5s 膨胀到 47s——这是 provider 侧的**隐性退化**，应用层无法改 DeepSeek 的速度。

## 六、最终方案：准入控制（背压）

### 6.1 原理
系统实测稳定容量约 50 并发（DeepSeek 不退化）。超过则**立刻 429 拒绝**，不放进来排队超时。
实现：`router.py` 入口加在途计数器，超过 `chat_max_concurrent=50` 立刻 `raise HTTPException(429)`。

### 6.2 1000 并发压测结果（准入控制前 vs 后）

| 指标 | 无准入控制 | **有准入控制** | 变化 |
|---|---|---|---|
| chat 总处理 | 66 | **16573** | 系统扛住 250x 流量 |
| 成功请求 | 0 | **21** ✅ | 全垮→有成功 |
| 失败特征 | 66个超时 49s | **16542个429(73ms)** | 慢死→快拒 ✅ |
| 失败耗时 | 49秒 | **73毫秒** | 670x ✅ |
| health p50 | 370ms | **180ms** | 系统不垮 ✅ |
| health 总数 | 107 | **1660** | 15x，全程健康 |

### 6.3 结论
- 准入控制将"系统雪崩"转化为"优雅降级"：超容请求 73ms 快速 429，系统稳定存活
- 21 个请求成功（之前 1000 并发是 0 成功）
- 成功请求 TTFT p50=19s（cap=50 仍在 DeepSeek 退化上沿；调低 cap 至 30 可优化 TTFT 但减少成功数）
- 这是企业级高并发的核心认知：**超容时保住系统，而非硬扛到全垮**

## 八、可写入简历的结论

> 主导 AI Agent 高并发优化，通过 Locust 7 档压测（1~1000 并发）分层定位瓶颈并逐级解决：
>
> ① **事件循环阻塞**：同步 `llm.invoke` 阻塞事件循环，P0 改造 `ainvoke` + `asyncio.gather`，
> 10 并发 health p95 从 120ms 降至 7ms（-94%）。
>
> ② **GIL 瓶颈**：通过"关 rerank 对照实验"实锤 reranker 的 GIL 绑定是新瓶颈；
> 受限于单机 16GB/4GB 显存无法多 worker，将本地 torch reranker 重构为硅基流动 rerank API
> （同款 bge-reranker-v2-m3，质量零退化），全链路异步 HTTP 化，
> 50 并发失败率从 84% 降至 0%，TTFT 47s→8.5s（5.5×）。
>
> ③ **外部 API 退化**：通过分步计时诊断定位 100+ 并发的剩余瓶颈为 DeepSeek LLM 的 GPU 分时退化
> （llm_ainvoke 从 2.5s 膨胀至 47s），实施准入控制与背压（在途计数 + 429 快速拒绝），
> 1000 并发下系统从"全垮"转为"优雅降级"：21 请求成功 + 16542 请求 73ms 快速 429，health 稳定 180ms。
